# WordPress Plugins - Testing Infrastructure

## Architecture

This repository is a **manifest-driven** shared testing/CI harness for **9 WordPress plugins**, each in its own subdirectory/git repo. `plugins.json` is the single source of truth for which plugins exist, where they live, and what they target — the Makefile, bootstrap, CI, and release automation all read it instead of hardcoding plugin lists. **Adding a plugin means adding one entry to `plugins.json`**, not editing a dozen files.

```
WordPress Plugins/
├── plugins.json               # THE manifest — read by everything below
├── bin/
│   ├── manifest.php            # CLI: list/query the manifest, build CI matrix, map changed files -> plugins
│   ├── check-versions.php      # Verify header/constant/readme/changelog version consistency
│   ├── extract-changelog.php   # Pull one version's changelog entry (used for GH release notes)
│   ├── setup-native.sh         # Set up a native (no-Docker) WP core + test lib for one WP version
│   └── bump-tested-up-to.php   # Tested-up-to bump logic (used by bump-tested-up-to.yml)
├── docker/                    # Docker environment (WordPress + MySQL)
│   └── docker-compose.plugins.yml   # Generated by `make compose` from plugins.json — don't hand-edit
├── tests/                     # All tests live here (outside plugin dirs)
│   ├── bootstrap.php          # Loads WP test suite + every manifest plugin + mocks
│   ├── phpunit.xml            # PHPUnit config with unit/integration suites
│   ├── _helpers/              # Base test case classes + Manifest.php (shared manifest/version helpers)
│   ├── _mocks/                # API mock interceptors + JSON fixtures
│   ├── _fixtures/             # Static fixture files (CSVs, sample files) for plugin tests
│   ├── unit/                  # Unit tests per plugin
│   └── integration/           # Live API tests (skipped without creds)
├── phpcs.xml                  # PHPCS config for all plugins
├── Makefile                   # Command runner — driven by bin/manifest.php, no hardcoded plugin lists
├── .github/workflows/         # Reusable CI/release/bump/claude workflows (see below)
├── docs/caller-workflows/     # Templates plugin repos copy into their own .github/
└── [9 plugin directories]     # Each is its own git repo (gitignored here)
```

## Quick Start (Docker)

```bash
make start          # Boot Docker (WordPress at http://localhost:8080); regenerates docker-compose.plugins.yml
make test           # Run all tests
make test-unit      # Unit tests only
make lint           # PHPCS lint all plugins (report-only — see CI)
make shell          # Shell into the WordPress container
```

## Quick Start (native, no Docker)

```bash
bin/setup-native.sh 6.9.1                      # downloads WP core + test lib, installs WooCommerce if needed
export WP_CORE_DIR=/tmp/wp-native/core-6.9.1
export WP_TESTS_DIR=/tmp/wp-native/tests-lib-6.9.1
export WP_TESTS_DB_HOST=localhost WP_TESTS_DB_NAME=wordpress_test WP_TESTS_DB_USER=wordpress WP_TESTS_DB_PASS=wordpress
export WP_TESTS_PHPUNIT_POLYFILLS_PATH=/path/to/vendor/yoast/phpunit-polyfills
make test-native
make test-plugin-native PLUGIN=wooflare
make lint-native
```

`bin/setup-native.sh` symlinks every plugin checkout it finds (by manifest `install_dir`) into `$WP_CORE_DIR/wp-content/plugins/`, so it works whether you have one plugin checked out or all nine. `PHPCS_BIN`/`PHPUNIT_BIN` env vars override the native binaries used by `*-native` Makefile targets if they're not on `$PATH`.

## The manifest (`plugins.json`)

```jsonc
{
  "defaults": {
    "php_runtime": "8.2",       // single PHP source of truth for Docker + CI
    "php_latest": "8.5",
    "wp_ci_floor": "6.4",       // WP test lib can't run on ancient WP — floor for the CI matrix
    "wc_latest_tested": "11.2",
    "wp_latest_tested": "7.1"
  },
  "plugins": [ /* one entry per plugin — dir, repo, svn_slug, install_dir, main_file,
                   version_constant, text_domains, requires_php/requires_wp, wc, dependencies,
                   api_mocks, fixtures, lint_exclude, integration_secrets, tests_dir */ ]
}
```

Query it with `bin/manifest.php` — `dirs`, `slugs`, `field <slug> <dotted.field>`, `matrix [--plugins=a,b] [--trunk]`, `affected <path>...` (maps changed files to plugin slugs; shared files map to every plugin), `check-headers` (manifest vs. plugin header drift, exits non-zero on mismatch), `compose` (emits `docker-compose.plugins.yml`).

## Testing Strategy

### Unit Tests (`tests/unit/`)
- Run without external dependencies
- API calls intercepted by mocks in `tests/_mocks/`
- Use `PluginTestCase` base class — includes `plugin_version($slug)`, which reads the *real* version from a plugin's own main-file header (never hardcode an expected version number in a test; it will drift)
- Safe to run anytime: `make test-unit` / `make test-native`

### Integration Tests (`tests/integration/`)
- Use live APIs (Cloudflare, Mandrill)
- Auto-skip when credentials missing (see each plugin's `integration_secrets` in the manifest)
- Use `IntegrationTestCase` base class
- Set credentials in `tests/.env` (copy from `.env.example`)

### API Mocking
Mocks use WordPress's `pre_http_request` filter to intercept HTTP before it leaves. No external mock server needed.

- `CloudflareAPIMock` - Intercepts `api.cloudflare.com` requests (cloudflare-ip-blacklist, wooflare)
- `MandrillAPIMock` - Intercepts `mandrillapp.com` requests (send-emails-with-mandrill)

Both support request logging (`::get_request_log()`, `::get_last_request()`), response overrides (`::set_response($pattern, $data)`), and fixture-based defaults (`tests/_mocks/fixtures/`).

### Fixtures (`tests/_fixtures/`)
Static files some plugins' tests need on disk — e.g. `tests/_fixtures/import-from-server/` (sample files for the server file browser/importer) and `tests/_fixtures/miller-media-csv-importer/` (sample CSVs). Never point a test at a real filesystem path outside this directory.

## Running Tests for a Single Plugin

```bash
make test-plugin PLUGIN=wooflare           # Docker
make test-plugin-native PLUGIN=wooflare    # native
```

`PLUGIN` is the manifest **slug** (see table above), not always the directory name — they're the same for every plugin here, but don't assume that holds for a future addition.

## Linting

```bash
make lint                           # All plugins (Docker)
make lint-fix                       # Auto-fix
make lint-plugin PLUGIN=wooflare    # Single plugin
make lint-native                    # Native, report-only, loops every plugin
```

PHPCS is WordPress Coding Standards + PHPCompatibilityWP for PHP 8.1+ (pinned versions — see Dockerfile). Lint is **report-only** everywhere, including CI — it never fails a build. Per-plugin exclusions (e.g. Mandrill's vendored `legacy/` wp_mail copy) come from each plugin's `lint_exclude` in the manifest via `bin/manifest.php lint-ignore`.

## Adding a Plugin

1. Add one entry to `plugins.json` (`dir`, `repo`, `svn_slug`/`wporg`, `install_dir`, `main_file`, `version_constant`, `text_domains`, `requires_php`/`requires_wp`, `wc`, `dependencies`, `api_mocks`, `fixtures`, `lint_exclude`, `integration_secrets`, `tests_dir`).
2. Add loading logic for it in `tests/bootstrap.php`'s `muplugins_loaded` block, following the existing pattern (see "Bootstrap loading strategy" below).
3. Add `tests/unit/<tests_dir>/` tests (at minimum an activation test asserting the real header version).
4. Run `php bin/manifest.php check-headers` and `php bin/check-versions.php <slug>` to confirm the manifest matches reality.
5. Copy the `docs/caller-workflows/` templates into the new plugin's own repo.

## Adding Tests

1. Create test file in `tests/unit/<tests_dir>/YourTest.php` (see `plugins.json` for each plugin's `tests_dir`)
2. Extend `PluginTestCase` (unit) or `IntegrationTestCase` (live API)
3. Name the file with `Test.php` suffix
4. Run `make test` / `make test-native` to verify

## Bootstrap loading strategy

`tests/bootstrap.php` decides, per plugin, whether to require the plugin's **whole main file** or just its **class files**:

- **Whole main file** when it's side-effect-light (expire-passwords, one-off-emails-for-woocommerce, miller-media-csv-importer with `WP_LOAD_IMPORTERS` predefined) — its own constants get defined naturally.
- **Class files only** when the main file unconditionally instantiates objects / registers hooks that would be redundant or noisy in tests (cloudflare-ip-blacklist, edit-usernames, protect-the-children, wooflare, import-from-server) or, for Mandrill, because loading the whole file would call `on_load()` and **replace `wp_mail()`** — only `lib/mandrill.class.php` and `lib/wpMandrill.class.php` are loaded, never the main file.

When a plugin's class files are loaded standalone, any constants they need are predefined with values **parsed live from that plugin's own main-file header** (`tests/_helpers/Manifest.php` → `mm_tests_plugin_header_version()`), never hardcoded — this is also what `PluginTestCase::plugin_version($slug)` uses.

## Key Design Decisions

- **Manifest-driven, not hardcoded** — `plugins.json` + `bin/manifest.php` are the only place plugin lists live.
- **Tests live outside plugin directories** so released plugins stay clean.
- **Docker provides an isolated environment**; native (no-Docker) testing is fully supported via `bin/setup-native.sh` and the `*-native` Makefile targets.
- **Separate test database** (`db-test` service in Docker) prevents test data from polluting the dev site.
- **WooCommerce is loaded only when a checked-out plugin actually declares a `woocommerce` dependency** (currently wooflare, one-off-emails-for-woocommerce).
- **`defaults.php_runtime` in `plugins.json` is the single PHP version source of truth** — the Dockerfile's `PHP_VERSION` build arg and the CI matrix's lower bound both derive from it (paired with each plugin's own `requires_php` and `defaults.php_latest`).
- **Lint is always report-only.** Only `check-versions` and the test suite itself can fail a build.

## Releasing a Plugin

Releases are driven by **tag push → reusable `release.yml` → the `wordpress-org` GitHub Environment**, which requires manual approval before anything touches SVN. There is no more "copy files into svn-deploy/ by hand" step in the normal path.

### 1. Version Bump

Each plugin stores its version in up to **3 places** — update all that apply (recall `edit-usernames` has no constant):

| Location | Example |
|----------|---------|
| Main plugin file header (`Version:`) | `* Version: 1.0.4` |
| Main plugin file version constant (see Plugins table) | `define('CFIP_PLUGIN_VERSION', '1.0.4');` |
| `readme.txt` (`Stable tag:`) | `Stable tag: 1.0.4` |

Run `php bin/check-versions.php <slug>` in the harness repo to verify all three (plus a matching changelog entry) before tagging — this is exactly what `release.yml`'s `verify` job re-checks against the tag.

### 2. Changelog

Add a new entry at the top of the `== Changelog ==` section in `readme.txt`:

```
= 1.0.4 =
* Description of change
```

### 3. Test & Lint

```bash
make test                              # or make test-native
make test-plugin PLUGIN=plugin-slug
make lint-plugin PLUGIN=plugin-slug    # report-only
php bin/check-versions.php plugin-slug
```

### 4. Commit, push, open a PR, merge to the plugin's default branch

The plugin repo's own `ci.yml` caller workflow (copied from `docs/caller-workflows/`) runs automatically and must produce a green **`ci-result`** check on the merge commit — that's the single check to require in that repo's branch protection.

### 5. Tag the release

```bash
cd plugin-directory/
git tag vX.Y.Z      # note the leading "v" — release.yml parses it
git push origin vX.Y.Z
```

This triggers the plugin repo's `release.yml` caller, which calls this repo's reusable `release.yml`:

- **`verify`** refuses to continue unless the *exact tagged commit* already has a successful `ci-result` check, the manifest's `wporg` is `true` for this slug, and `bin/check-versions.php <slug> <tag-version>` passes.
- **`deploy`** requires approval on the `wordpress-org` Environment, then runs `10up/action-wordpress-plugin-deploy` (respecting the plugin's own `.distignore` — see `docs/caller-workflows/.distignore` for the standard exclusion list) and creates a GitHub release with that version's changelog entry.

`miller-media-csv-importer` has `wporg: false` — tagging it only ever creates a GitHub release flow failure at the `verify` step by design; it is **never** deployed to SVN.

### Emergency manual SVN fallback

Only if the automated `release.yml` path is broken. SVN working copies live in `svn-deploy/<svn-slug>/` (checked out from trunk). **Respect the plugin's `.distignore`** — never copy `.git`, `tests/`, `CLAUDE.md`, `README.md` (when a `readme.txt` exists), `composer.*`, `node_modules`, etc. into the SVN working copy.

```bash
# Copy only the files that should actually ship (per .distignore) from the git repo to SVN trunk
cp plugin-directory/changed-file.php svn-deploy/svn-slug/changed-file.php

cd svn-deploy/svn-slug/
svn commit -m "X.Y.Z: Summary of changes"

svn copy https://plugins.svn.wordpress.org/svn-slug/trunk \
         https://plugins.svn.wordpress.org/svn-slug/tags/X.Y.Z \
         -m "Tag X.Y.Z"

cd plugin-directory/
gh release create X.Y.Z --title "X.Y.Z" --notes "$(php ../bin/extract-changelog.php readme.txt X.Y.Z)"
```

### Quick Checklist

- [ ] Version bumped everywhere that applies (header, constant if any, readme stable tag)
- [ ] Changelog added to readme.txt
- [ ] `php bin/check-versions.php <slug>` passes
- [ ] Tests + lint pass, PR merged to default branch with a green `ci-result`
- [ ] Tag pushed (`vX.Y.Z`)
- [ ] `release.yml` `verify` job green
- [ ] `wordpress-org` Environment approval given
- [ ] GitHub release created (automatic on success)

## CI/CD

### Workflows (`.github/workflows/`)

- **`ci.yml`** — reusable (`workflow_call`, inputs `plugin`, `harness_ref`) and directly triggered here on `pull_request`/`push` to `main`. Jobs: `changes` (maps changed files to affected plugin slugs via `bin/manifest.php affected`), `matrix` (`bin/manifest.php matrix --trunk`), `test` (one native run per plugin × PHP × WP, PHPCS report-only as an artifact + step summary, `bin/check-versions.php`), and **`ci-result`** — the single required check; it fails if `changes`/`matrix` didn't succeed or any `test` leg genuinely failed (allow-failure `trunk` legs don't count against it).
- **`release.yml`** — reusable deploy workflow described above. Secrets: `SVN_USERNAME`, `SVN_PASSWORD` (required), `HARNESS_DEPLOY_KEY` (optional, see caveat below).
- **`bump-tested-up-to.yml`** — scheduled weekly (+ `workflow_dispatch`); checks `api.wordpress.org` for the latest WP/WooCommerce versions, and opens a PR in any plugin repo whose `Tested up to` / `WC tested up to` is behind (never touches Version/Stable tag). Logic lives in `bin/bump-tested-up-to.php` so it's runnable/testable locally with `--dry-run`.
- **`claude-issue.yml`** — reusable + used here; lets Claude Code implement an issue labeled `claude` (or a comment mentioning `@claude` from an OWNER/MEMBER/COLLABORATOR) on a new branch and open a PR. Never merges, tags, or deploys.
- **`.github/dependabot.yml`** — weekly, grouped GitHub Actions updates.

### Required check to configure

Set branch protection (on both this repo and every plugin repo) to require **`ci-result`** only — it's the aggregate job and is designed to be the single gate.

### Pinned actions

Third-party actions are pinned to **major-version tags** (`actions/checkout@v4`, not a commit SHA) rather than exact commit SHAs, because this environment can't look up current SHAs offline. `.github/dependabot.yml` keeps those tags current — treat its weekly PRs as routine.

### ⚠️ Private harness repo + public plugin repos

`Miller-Media/wordpress-plugin-tests` (this repo) is private; most plugin repos are public. **GitHub does not allow a public repo to call a reusable workflow defined in a private repo.** Until Matt picks one of the following, `ci.yml`/`release.yml` callers in the public plugin repos will fail to invoke this repo's workflows:

1. **Make this repo public.** It contains no secrets (every secret is supplied by the calling repo via `secrets: inherit` / environment protection), so this is the simplest fix.
2. **Enable "Accessible from repositories in the organization"** on this repo's Actions settings — this only unblocks *private* caller repos in the same org; it does **not** help public plugin repos.

See `docs/caller-workflows/README.md` for the full explanation and the caller templates themselves.

## Native test environment reference

Useful env vars for `*-native` Makefile targets and `tests/bootstrap.php` directly:

| Var | Purpose |
|-----|---------|
| `WP_CORE_DIR` | Path to a WP core checkout (with plugins symlinked in by `install_dir`) |
| `WP_TESTS_DIR` | Path to the WP PHPUnit test library (`includes/`, `data/`) |
| `WP_TESTS_DB_HOST` / `_NAME` / `_USER` / `_PASS` | Test database connection |
| `WP_TESTS_PHPUNIT_POLYFILLS_PATH` | Explicit path to `yoast/phpunit-polyfills` (falls back to `$COMPOSER_HOME/vendor/...`, then `/root/.composer/vendor/...`) |
| `PHPCS_BIN` / `PHPUNIT_BIN` | Override the binaries used by `lint-native` / `test-native` if not on `$PATH` |

`bin/setup-native.sh <wp-version> [options]` provisions `WP_CORE_DIR`/`WP_TESTS_DIR` from scratch (WP core + matching develop.svn test lib + WooCommerce if any manifest plugin needs it + plugin symlinks); see its `--help`-style header comment for all options.

**Never commit real credentials.** `tests/.env` is gitignored; copy `tests/.env.example`.
